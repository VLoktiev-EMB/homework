<objective>
Run the phase's one dated on-hardware acceptance sequence — build, flash, monitor — settle the console-port choice by measurement, and write the phase log that every later phase reads as this phase's evidence.

Purpose: criteria 2 and 5 cannot be discharged by reading anything. The eFuse-derived banner and the firmware's own PSRAM report are the only evidence that the attached module is really the 16 MB / 8 MB variant, and the firmware report is only meaningful because the fragment now enables PSRAM — a build that never enabled it cannot report it. This plan is also where the console decision stops being a documentation-derived assumption and becomes a reading.

**Phase split, stated explicitly rather than left implicit.** Phase 2 is planned as two halves: plans 02-01 and 02-02 carry everything a machine can prove offline, and this plan carries the physical run. Neither offline plan claims criterion 2 or criterion 5's console half, and this plan does not claim them either unless the readings exist. No board is attached as this plan is written, so the expected outcome is that the physical slots stay explicitly unfilled and the phase log reports criteria 2 and 5's console half as UNMET. That is the honest outcome and it is to be reported, not softened: the run is written so it goes green on its own contract — every reading verbatim or visibly absent, and the criteria's status stated — and never so it goes green on a reading nobody took.

Output: the phase log, `.planning/phases/02-board-and-environment-baseline-n16r8-acceptance-gate/02-03-SUMMARY.md`.
</objective>

**Step 0 — identify the port. This is the run's step zero, not an assumption.** Take the serial-device inventory in its machine-readable form and record it. Then attach the board by its UART socket — the socket beside the one labelled USB, not the firmware-created one — and take the inventory again. Record both readings and the difference. The literal device node that appears is this run's own observation: it belongs in the phase log and nowhere else in the repository.

If nothing new appears, first check what the system reports for USB before drawing any conclusion about the board, and record what that shows. A board that enumerates as a USB device but presents no serial node is a different finding from a board that does not appear at all, and the two have different remedies. Then continue through the remaining steps, which will each fail; record each failure's exact output.

**Settle the console by measurement.** Compare the node the board presented against the pattern the fragment carries. State which socket was used, which node appeared, whether the committed pattern matched it, and whether the pattern matched anything else in the inventory. If the measurement disagrees with the committed pattern, correct the pattern in `shared/pio/base.ini` to the measured form — still a pattern, never a literal node — mirror the correction into the documents that name it, re-run the build and the configuration reading so the correction is proven not to have broken anything, and commit all of it with a message scoped to the correction. Record both the pattern that did not match and the pattern that did.

**Step 1 — build and flash.** Build and flash the baseline by its project directory. Record the upload output verbatim, including the connect banner. The banner carries the chip identity and a features line; the feature to look for on this module is the in-package PSRAM entry. Note that the banner does **not** carry the flash size for this module — the flash die is external, so the eFuse field that would name an in-package flash size is empty and no flash entry is printed. Do not record the absence of a flash entry as a failure; it is the expected shape. The banner may also carry a USB-mode line; if it does, record it, because it is the eFuse-level statement bearing on the console decision.

**Step 2 — the flash die.** Invoke the flasher's own identifier with the chip explicitly named and the port explicitly passed. Never omit the port: with no port it auto-detects, silently selects an unrelated device on this machine, and fails for a reason that has nothing to do with the board. Record its output verbatim and read the detected flash size from it. This is the only reading that names the physical flash die.

**Step 3 — the firmware's own report.** Open the serial monitor for the baseline environment and record the line the firmware prints exactly as it arrives. That line carries the flash size the runtime reports, whether PSRAM was found, and the PSRAM size. This reading is the one that proves the **build** enabled PSRAM, which is why it is asked for in addition to the two eFuse readings rather than instead of them. If the monitor prints nothing at all, that is itself a finding worth recording — a socket or console mismatch produces exactly that shape, a successful flash followed by silence — so record it as printed and do not retry silently until something appears.

**Step 4 — close the tree.** If any correction was committed in this task, confirm the porcelain report is empty now. This reading is taken here, before the phase log exists, because the log is itself a new unignored file under a tracked directory and a reading taken after it is written would fail over the log rather than over the thing under test.
