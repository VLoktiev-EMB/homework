## Critical Issues (BLOCKER)

### CR-02: `isRepoOwnedIgnoreSource` exempts the root `.gitignore` from the very check it exists to perform — a silent false green

**File:** `tools/tests/ignore-rules.test.mjs:59` (function `58-63`, exercised by test 1 at `136-145`)

**Issue:** The function's docstring asks one question — "Does a clone of this repository actually inherit
the file git reported as the source?" — and answers it with `git ls-files` for nested files. For the root
file it answers without asking:

```js
if (source === IGNORE_FILE) return true;   // :59
```

The docstring states the exemption as a fact ("The root `.gitignore` always qualifies", `:50`). Nothing
checks it. Because `git check-ignore` reads ignore files from the **working tree**, not the index, every
`MUST_BE_IGNORED` member whose source is the root file keeps resolving, keeps its `protects` promise, and
keeps the suite green — while a clone carries none of those rules.

Reproduction (throwaway fixture under `/tmp`, fresh `git init`, byte-identical copies of the root
`.gitignore` and `homeworks/project-baseline/.gitignore`, the five tracked planning files the suite
requires):

| state | `node --test tools/tests/ignore-rules.test.mjs` |
|---|---|
| control | `tests 5 / pass 5 / fail 0` |
| `git rm --cached .gitignore` (file still on disk) | `tests 5 / pass 5 / fail 0` |

In the second state test 1 reports `✔ every machine-local artifact resolves to an ignore file this
repository tracks`, `git ls-files | grep gitignore` returns **only** the nested file, and git still happily
answers:

```
$ git check-ignore -v .planning/state.json .DS_Store server.pem
.gitignore:95:.planning/state.json	.planning/state.json
.gitignore:82:.DS_Store	                .DS_Store
.gitignore:108:*.pem	                server.pem
```

Every rule that `.gitignore`'s own header (`:103-111`) added so "a secret [cannot] reach a public
repository" is now absent from a clone, and the file whose printed name is *"an ignore file this repository
tracks"* is the one untracked file in the set. Tests 3, 4 and 5 are all green in the same state: test 3
(`:162`) sees no tracked file matching an on-disk rule, test 4 checks `.planning/*.md`/`json` only, and
test 5 reads the file from the working tree.

Two honest qualifiers. **This repository is not exposed today** — `git ls-files --error-unmatch .gitignore`
exits 0, and `git rm --cached .gitignore` leaves the file visible as untracked in `git status --porcelain`,
so an attentive operator would catch it by hand. And this is the same class the `15:00:47Z` report rated
Critical in `CR-01`: a guard that returns success without performing its check, where the check is the
file's entire purpose. It is rated Critical for the same reason, with the same caveat — the exposure is
latent, the false green is not. Note the asymmetry the function creates: nested sources must prove
tracked-ness, the root source is trusted, and the root source is the one carrying the secrets section.

**Fix:** delete the pass-through. The basename test at `:61` already admits `.gitignore`, and `git ls-files
--error-unmatch -- .gitignore` answers correctly for it (measured: exit 0 here).

```js
function isRepoOwnedIgnoreSource(source) {
  // No pass-through for the root file. It is the file whose disappearance this test exists to
  // catch, and git reads ignore files from the working tree, so "git found a rule" says nothing
  // about whether a clone has the file. It answers the same question as a nested one.
  if (source.startsWith("/") || source.split("/").includes("..")) return false;
  if (source.slice(source.lastIndexOf("/") + 1) !== IGNORE_FILE) return false;
  return git(["ls-files", "--error-unmatch", "--", source]).status === 0;
}
```

Measured in the fixture: with the fix applied, the healthy tree is still `5/5 pass`, and with
`git rm --cached .gitignore` the suite goes red as it should (`fail 1`). Keep the docstring's sentence and
make it an asserted claim rather than an assumption; a one-line mutation case — untrack the source, expect
red — pins it, in the same style the file already uses for its other claims.

### WR-11: The inline-comment guard rejects a valid escaped-hash pattern

**File:** `tools/tests/ignore-rules.test.mjs:189-199` (the pattern is `:196`)

**Issue:** Still live, re-verified this run; line numbers updated from the prior report's `:169-179`.
`/^[^#][^#]*#/` means "first character is not `#` and some `#` appears later" — the right idea, because
gitignore has no inline comments. But git allows a leading `#` to be **escaped**, which is the only way to
ignore a file whose name starts with `#`:

```
$ printf '\\#literal.txt\n' > .gitignore     # two bytes: \ #
$ git check-ignore -v '#literal.txt'
.gitignore:1:\#literal.txt	#literal.txt
exit=0
```

The guard flags that same line as an offender. Measured against the two candidate regexes:

| line | `/^[^#][^#]*#/` (current) | `/^[^#][^\n]*?(?<!\\)#/` |
|---|---|---|
| `\#literal.txt` | **true** (offender) | false |
| `foo\#bar` | **true** (offender) | false |
| `foo # comment` | true | true |
| `# comment` | false | false |

A correct, necessary rule therefore turns the suite red and tells the author that gitignore has no escaped
hashes, which is false. The trigger is narrow (no such line exists today) but the failure is blocking: the
gate refuses a valid edit and offers no path forward except deleting the rule or weakening the test.

**Fix:** as above, plus a mutation case rather than prose. `(?<!\\)` covers the single-backslash case that
occurs; if double-escaping must be exact, invert the test — match `/^(?:[^#\\]|\\.)*#/` — and keep the
message. Either way the comment at `:189-193` should name the escape, because as written it teaches the
opposite.

### WR-14: The newly committed `extensions.json` contradicts `.editorconfig`'s JSON indentation rule — the mirror image of WR-04

**File:** `homeworks/project-baseline/.vscode/extensions.json:5-10` against `.editorconfig:22-23` and
`.vscode/settings.json:11`

**Issue:** New. `.editorconfig:22-23` assigns `indent_size = 2` to `[*.{json,jsonc,yml,yaml,ini,cfg,properties}]`,
and `.editorconfig:1-2` states the governing principle ("One owner per rule"). Measured indentation:

| file | leading-space widths present |
|---|---|
| `.vscode/extensions.json` (committed by the phase) | `2, 4` |
| `homeworks/project-baseline/.vscode/extensions.json` (committed by this commit) | `4, 8` |

The file is PlatformIO's generated template, so 4 spaces is what the generator emits; the point is that

`homework.code-workspace` (same root cause, opposite direction).

**Fix:** decide which owner wins and record it, rather than leaving two committed owners disagreeing. The
cheapest option keeps the generated file untouched and makes `.editorconfig` explicit about it, in the
same style as the `[Makefile]` section:

```ini

```

it; if it does, this same decision recurs on every project regeneration. Either way, add the resulting

### IN-07: The ignore-contract test cannot tell "git could not run" from "the rule was widened"

**File:** `tools/tests/ignore-rules.test.mjs:29-31`, `:41-44`, `:149-154` (new call site: `:62`)

**Issue:** Still live, re-verified this run; line numbers updated from the prior report's `:26-28`,
`:37-42`, `:129-134`. `git(args)` returns the raw `spawnSync` result and no caller inspects
`result.error`, so both failure paths collapse "git could not answer" into a confident diagnosis about the
rules. Re-measured this run by running the test file in a directory that is not a repository (git present
on `PATH`, `check-ignore` exits 128 — `fatal: not a git repository`):

```
✖ every machine-local artifact resolves to an ignore file this repository tracks
✖ every hand-authored or tracked counterpart stays unignored
✖ no tracked path is hidden by the ignore configuration
✖ the tracked planning data the phase ships is still tracked
✖ no line outside column 1 of the ignore file carries a comment marker
ℹ tests 5 / pass 0 / fail 5
```

Both rules-related messages are wrong — nothing about the rules changed — and the same misdiagnosis
occurs when git cannot be spawned at all (`status` is `null`). `da63b0a` adds a **third** call site in this
class at `:62`: a failed `git ls-files` returns `false`, i.e. the confident claim "which a clone does not
inherit". It is masked today only because `ignoreSource` (`:42`) returns `null` first and the earlier
assertion fires, so the new call site does not create a new wrong message — but the pattern is still
spreading. This is a diagnostics defect, not a false green: every path fails loudly.

**Fix:** surface the spawn error once, in `git()`:

```js
function git(args) {
  const result = spawnSync("git", args, { cwd: REPO_ROOT, encoding: "utf8" });
  if (result.error) throw new Error(`git ${args.join(" ")} failed to start: ${result.error.message}`);
  return result;
}
```

and in the unignored test either accept `1` or `128` with a message naming which was seen, or keep `=== 1`
but include `result.stderr` in the assertion message so `fatal: not a git repository` is visible. `git` is
intrinsic to this repository, so this needs no skip guard.
