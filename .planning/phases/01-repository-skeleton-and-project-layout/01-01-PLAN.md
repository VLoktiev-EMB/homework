<objective>
Prove the repository's thinnest end-to-end path — a homework folder on disk that the tool layer discovers, that a generated workspace file lists, and that PlatformIO builds from the repository root with one command — and commit it, so every later phase builds on a skeleton that already works.

Purpose: this is the Walking Skeleton (see `SKELETON.md`). Everything else in Phase 1 — the sweep, the ignore rules, the documentation — is expansion on top of a path that has already been proven to run. It also removes the risk the research names as "the first homework being the first thing ever flashed": the committed baseline becomes Phase 2's acceptance vehicle.
Output: `tools/lib/discover.mjs`, `tools/generate-workspace.mjs`, the committed `homeworks/project-baseline/` project, the generated-but-committed `homework.code-workspace`, the three test files and `shared/lib/README.md`.

Two layout decisions this plan implements directly. **All repo-owned tooling lives in one folder, `tools/` (D-09)** — the research's split across a generators folder and a shell-scripts folder is collapsed, not carried forward, so there is one folder and one language to look in. And **the baseline project is committed to the repository (D-10)** rather than created as a scratch proof, so success criteria 1 and 2 are provable from a clone by anyone and the project also serves as Phase 2's acceptance vehicle; its accepted consequences are that Phase 2 rewrites its environment file and that it must be deliberately retired before the Phase 8 README index lists it as a homework.

Build the thinnest path that touches every layer this phase owns: a folder on disk, discovered and validated by the tool layer, listed by a generated workspace file, and built by PlatformIO from the repository root.

1. Create the tree deliberately — never with `pio project init`, which writes its own 5-byte per-project `.gitignore` and, with `--ide vscode`, aborts with `ProjectEnvsNotAvailableError` on an environment-less ini. Two ignore files where one is invisible is a trap.

2. `tools/lib/discover.mjs` — the single discovery and validation source (verified implementation at `01-RESEARCH.md` lines 454-510; reproduce its contract exactly). Node ESM importing only `node:fs` and `node:path`; no third-party glob, no argument parser.
   - `HOMEWORKS_DIR = "homeworks"`.
   - `ID_PATTERN = /^(?:m[0-9]{2}-l[0-9]{2}|project)-[a-z0-9]+(?:-[a-z0-9]+)*$/` — the two-branch alternation from D-05 plus D-06. Also export `ID_PATTERN_TEXT`, the same pattern as a string without slashes, so the sweep can quote the expected pattern in a failure message.
   - An internal directory lister over `readdirSync(dir, { withFileTypes: true })` that filters on `isDirectory()`, maps to names and sorts. The `isDirectory()` filter is the symlink-escape control — it is **false** for a symlink — so a symlinked directory under `homeworks/` can never walk the filesystem. It must return an empty array when the directory does not exist, never throw. Do not filter dot-directories explicitly; `homeworks/` has none and the sort must stay the only ordering rule.
   - `findDepthViolations(repoRoot)` — a bounded walk below `homeworks/` collecting the repo-relative path of every `platformio.ini` found at depth 1 or deeper inside a homework folder, sorted. It must be a pure filesystem walk that does not compile anything, so it fires in the same second a folder is misplaced.
   - `discoverHomeworks(repoRoot)` returning one object `{ found, malformed, violations }` where `found` items are `{ id, dir }` with `dir` spelled `homeworks/<id>`. One call must return everything all three consumers need, so a consumer that only wanted the list cannot skip validation.
   - `envNames(id)` returning the project-scoped pair from D-16: hyphens stripped from the id, then `_s3` and `_native` appended. `envNames("project-baseline")` must yield `projectbaseline_s3` and `projectbaseline_native`.
   The id regex is applied **before** a name is ever interpolated into a path or handed to a child process; its character class excludes `.` and `/`, so traversal is impossible by construction.

3. `homeworks/project-baseline/platformio.ini` — exactly one environment, `[env:projectbaseline_s3]`, whose name is `envNames("project-baseline").s3`. It carries `platform = espressif32@7.1.3` (an exact pin — never a range, never the unreleased development branch), `board = esp32-s3-devkitc-1`, `framework = arduino`, and the four measured N16R8 overrides: `board_upload.flash_size = 16MB`, `board_build.partitions = default_16MB.csv`, `board_build.arduino.memory_type = qio_opi`, `build_flags = -DBOARD_HAS_PSRAM`. Add `monitor_speed = 115200`.
   - **Do not add a native environment.** D-16 fixes the normalization rule for both environments and this plan fixes the *name* the native one will carry, but the environment itself belongs to Phase 5 (VERIFY-01): `pio run -d` with no `-e` builds every environment in the file, and an Arduino-only source tree cannot compile under `platform = native`, so adding it now would break the one-command build that is criterion 2. Record this reason in the baseline README in task 3.
   - **Do not add `upload_port` or `monitor_port`** (D-12). `pio device list` shows no usable port on this machine and the repository is public. Phase 2 adds the port and console decision after the acceptance run.
   - `default_4MB.csv` must not be referenced: it is not shipped in the pinned Arduino core.

4. `homeworks/project-baseline/src/main.cpp` — `#include <Arduino.h>`, a `setup()` that calls `Serial.begin(115200)` and one `Serial.printf` reporting `ESP.getFlashChipSize()`, `psramFound()` and `ESP.getPsramSize()`, and an empty `loop()`. This is D-14's serial report, and it is exactly what Phase 2's acceptance criterion 2 needs to see over the monitor.
   - **Touch no GPIO.** Name no pin-driving API anywhere in the file, comments included. A blink was rejected because the RGB-LED pin is unverified (GPIO48 on the initial revision versus GPIO38), and committing a pin-mode call for an unverified pin is precisely the failure AGENT-05 later formalises. Write no comment that names a pin-driving API either — the acceptance gate greps the source and must not trip on prose.
   - `Serial.begin`'s baud must match the ini's `monitor_speed`.

5. `tools/generate-workspace.mjs` — the generator and its drift check (verified implementation at `01-RESEARCH.md` lines 521-560). Node ESM with a shebang, importing `discoverHomeworks` from `./lib/discover.mjs`. Resolve the repository root from `import.meta.url` through `fileURLToPath` and `dirname` up one level, so the script works from any working directory rather than hardcoding a cwd.
   - Export `renderWorkspace(repoRoot)` — a **pure** function returning the file's text. It emits one top-level key, `folders`, whose entries are, in this order: the literal name `root` with path `.`; the literal name `shared` with path `shared`; then one entry per discovered id, named by the id and pathed at the id's directory. Serialise with `JSON.stringify(value, null, 2)` followed by exactly one newline. Emit **no comments**: VS Code accepts JSONC, which makes a hand-added comment a plausible edit that any byte comparison would flag.
   - The CLI accepts `--check`. Without it, write the rendered bytes to `homework.code-workspace` at the repository root and print the absolute path written. With it, compare the on-disk bytes against freshly rendered bytes: exit 0 printing that the file is up to date, or exit 1 printing a three-line message naming the file, stating that it is generated from the filesystem and must never be hand-edited, and giving the exact command to regenerate it.
   - Prefer `--check` over a git-diff form: it works outside a git checkout, does not depend on the file being tracked, and can print the rule and the remedy instead of a raw diff.
   - Three determinism requirements, all load-bearing for the drift check to be stable: sort every list; fix the key order and the serialisation; never emit comments.

6. Run `node tools/generate-workspace.mjs` once to create `homework.code-workspace`. Do not author that file by any other means.

Do not create `docs/`, `shared/pio/`, any `scripts/` folder, a `package.json`, or a `platformio.ini` at the repository root or under `shared/`. A root ini would give the IDE a second candidate for "active project" and, with no `[env:]` section, would make `pio run -d` exit 1.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| filesystem → tool layer | Directory names under `homeworks/` are untrusted input: they become a path segment and an argument to a child process. |
| filesystem → generated artifact | The tree decides the content of `homework.code-workspace`; a name that matches the grammar is copied verbatim into a committed file. |
| repo → public remote | Anything committed is world-readable forever. The course instructor and possibly employers read this history. |
| tool layer → PlatformIO | The tool layer spawns `pio` with a path it derived. No shell is involved. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-1-01 | Tampering | `discoverHomeworks` → `homeworks/<id>` path interpolation | medium | mitigate | The frozen id regex is applied **before** the name becomes a path or a child-process argument; its character class excludes `.` and `/`, so traversal is impossible by construction. |
| T-1-02 | Tampering / Information Disclosure | `findDepthViolations` walk | medium | mitigate | The walk uses `readdirSync` with `withFileTypes: true` and filters on `isDirectory()`, which is false for a symlink, and it is rooted at `homeworks/`. A symlink can neither be followed out of the repository nor cause an unbounded walk. |
| T-1-03 | Information Disclosure | `homework.code-workspace` and the baseline `platformio.ini` | high | mitigate | No machine-local absolute path, no personal port and no unverified board fact is committed. The generator emits only repo-relative paths; the ini deliberately omits both port keys; the baseline drives no GPIO. A committed port or pin would be either a private machine detail or a build-breaker on another machine. |
| T-1-04 | Tampering | the generated workspace file | medium | mitigate | The file is generated from the filesystem and guarded by `--check`, which compares on-disk bytes against freshly rendered bytes. A hand-edited file is detected and named rather than silently trusted. |
| T-1-05 | Denial of Service | tooling with no lockfile | low | accept | Zero third-party dependencies means there is nothing to pin and nothing to hijack; the tool layer imports only `node:` built-ins and `node:test` ships with the runtime. | T-1-SC | Tampering | npm/pip/cargo installs | high | mitigate | This plan installs **no** package: no `package.json`, no `requirements.txt`, no `pio pkg install`, no new PlatformIO dependency.
