## Форма шва (мова + межа)

Спочатку власник поставив зустрічне питання: «я б насправді обрав чистий C для дефолтної мови, так як він може бути використаний всюди, на стм32 і тд, твої думки?» — тобто це не вибір з підготовлених опцій, а власна пропозиція.

| Option | Description | Selected |
|--------|-------------|----------|
| Чистий C як дефолт | C компілюється всюди (STM32 тощо); ESP-IDF — теж C-фреймворк, тож шов реалізується з обох боків без адаптера | ✓ |
| C++ як дефолт | Звичніше для Arduino, доступні шаблони й RAII | |
| Залишити як є | `c++17` з metadata скэффолда | |

**User's choice:** Чистий C.
**Notes:** Власник підтвердив після того, як я виміряв, що framework сам компілює `.c` як `-std=gnu99` (`platformio-build-esp32s3.py:44-45`), а `.cpp` — як `-std=gnu++11` (`:49-50`). Ключовий аргумент, який переважив: ESP-IDF — це C-фреймворк, тому C-ABI шов робить `SHARED-03` правдою не декларативно, а матеріально. Побічний ефект — різке звуження D4.

### Чи можна домашки теж на чистому C?

| Option | Description | Selected |
|--------|-------------|----------|
| Чистий C усюди | Логіка і шим обидва на C | |
| C де можливо, C++ за потреби | Логіка на C, шим на C++ — вирішувати при створенні домашки | ✓ |
| Усе C++ | Не турбуватись про розділення | |

**User's choice:** «домашки за можливістю також на чистому, але іноді можна й на плюсах, але це обговорювати при створенні мабуть?»
**Notes:** Довелося виправити одне припущення. `src/main.cpp` **не може** бути на C: виміряно, що `cores/esp32/Arduino.h:149-150` оголошує `setup()`/`loop()` без `extern "C"` (тобто з C++-зв'язуванням), а `cores/esp32/main.cpp:42,50` — це C++, який їх кличе; файлу `main.c` у ядрі немає. Власник прийняв формулу «тонкий C++ шим + логіка на C». Питання «чи обговорювати при створенні» — так, це Phase 7 (`AGENT-04`).

### Де живе Arduino-бекенд?

| Option | Description | Selected |
|--------|-------------|----------|
| Бекенд у shared/lib | Один спільний на весь репозиторій; написати раз, протестувати раз | ✓ |
| Бекенд у кожній домашці | Правило без винятків, залежність від платформи видно явно | |

**User's choice:** Спершу «я не сильно розумію як це працює - поясни простіше», потім — після пояснення через файлові дерева й аналогію з розеткою — «Один спільний».
**Notes:** **Ключове уточнення від власника, яке змінило розрахунок:** перехід Arduino→IDF **часовий** — ранні домашки на Arduino і такими лишаються, пізні на IDF, мішаються дуже рідко. Тобто старі домашки нікуди не мігрують, і шов потрібен не для них, а щоб **спільний шар** пережив зміну фреймворку. Це підсилило аргумент за спільний бекенд, а не послабило його.

### Чи може бекенд теж бути чистим C?

Виміряно, без варіантів на вибір — це факт, не рішення: `esp32-hal-uart.h:18-19,45-46` тримає `uartBegin()`/`uartWrite()` у `extern "C"`, `esp32-hal.h:41,137-139` тримає `millis()`/`delay()` у `extern "C"`. Тобто ядро Arduino 2.x саме влаштоване як C-шар під тонкою C++-обгорткою. «Shared = чистий C» досяжно повністю, включно з бекендом.

| Option | Description | Selected |
|--------|-------------|----------|

Критерій 2 усе одно доводиться — зміною рядка у виводі firmware. Другий аргумент: логування — найбільш перевикористовувана річ у курсовому репо, тож `emb_log` не є мертвим кодом.

## Правила seam-чека

### Набір патернів

| Option | Description | Selected |
|--------|-------------|----------|
| Точні шляхи + закрити дірку | Матчити шлях інклюда, а не підрядок; додати `esp32-hal-` | ✓ |
| Буквально, дірку — в беклог | Рівно чотири патерни з критерію 3 | |

**User's choice:** Точні шляхи + закрити дірку.
**Notes:** Я виявив, що критерій 3 у буквальному вигляді **одночасно** пропускає справжній ESP32-HAL і хибно ловить сторонню бібліотеку:
- `esp32-hal-gpio.h` — це framework-заголовок, але під `esp_*` не підпадає, бо починається з `esp32-`, а не `esp_`
- `ArduinoJson.h` — це третій-стороння бібліотека, але наївний пошук підрядка «Arduino» її спіймає

Розходження з буквальним текстом критерію записується як датована поправка — за прецедентом accepted override Фази 1.

### Механізм виключення

| Option | Description | Selected |
|--------|-------------|----------|
| Названий список у чеку | Один рядок `ALLOWED = ["emb_hal_arduino"]` | ✓ |
| Поле `frameworks` у library.json | Бекенд оголошує себе сам, чек не правиться | |
| Патерн `emb_hal_*` | Нуль правок узагалі | (розглянуто і відкинуто) |

**User's choice:** «щоб було менше тертя» — тобто критерій, а не один з варіантів.
**Notes:** Я ухвалив рішення за цим критерієм і обґрунтував. Поле `frameworks` вимагало б парсингу кожного маніфесту (нове джерело збоїв і нова залежність від формату), плюс семантика поля — «сумісна з фреймворком», а не «вміє framework-заголовки», тож правило перетворилось би на здогад. Патерн `emb_hal_*` не вимагав би правок узагалі, але тихо звільняв би будь-яку папку з таким іменем — дірка ширша за ту, яку фаза закриває. Названий список правиться один раз у житті проєкту.

## D4: C++ стандарт

Варіантів на вибір не було — питання закрилося виміром. `platformio-build-esp32s3.py:44-45` задає `CFLAGS = -std=gnu99`, `:49-50` задає `CXXFLAGS = -std=gnu++11`.

**User's choice:** n/a — виміряно.
**Notes:** Це закриває MEDIUM-confidence прогалину, яку `STACK.md:185` і `PITFALLS.md:129` лишали відкритою, і **прибирає цілий клас проблеми**: дрейф C++-стандарту (`gnu++11` → `gnu++2b` → `gnu++26`) більше не торкається shared-шару взагалі. Стеля для shared-коду — C99: немає `_Static_assert`, немає `stdatomic.h`.

## Розкладка library.json

| Option | Description | Selected |
|--------|-------------|----------|
| Стандартна розкладка | `library.json` + `include/` + `src/`; нуль магії в маніфесті | ✓ |
| Пласка (як у research) | Файли в корені + явна `build`-секція | |

**User's choice:** Стандартна розкладка.
**Notes:** Виміряна пастка, яку це обходить: LDF за замовчуванням шукає джерела в `src/`, тож бібліотека, чиї джерела лежать деінде, компілює заголовки, але **тихо відкидає одиниці трансляції** → `undefined reference`, що вказує не туди, де причина. `srcDir: "."` зі `srcFilter` — це виправлення тієї пастки, а не перевага. Деталь на користь стандартної розкладки, яку я відзначив окремо: `emb_hal_arduino` (бекенд) не повинен мати публічного заголовка взагалі, і розділення `include/` проти `src/` робить цю межу структурно видимою.

Зафіксовано як живий ризик: `platform = native` очікує системний GCC, а `/usr/bin/gcc` на цій машині — шим Apple clang, ще не перевіряли.
